# Contributing to PocketAuthor

Thank you for helping improve PocketAuthor.

PocketAuthor spans authoring software, publishing workflows, public knowledge, directories, research, production tooling, accessibility, and community resources. Contributions should make the system more useful, trustworthy, accessible, and easier to understand.

## Where to contribute

- **Public docs, positioning, workflows, research, and community content:** [PocketAuthor-Public](https://github.com/Pocket-Author/PocketAuthor-Public)
- **Product engineering:** [PocketAuthor](https://github.com/Pocket-Author/PocketAuthor)
- **Organization-level community files:** this `.github` repository

Repository-specific contributing instructions take precedence over this shared guide.

## Before opening an issue

Search existing issues first. If an issue already covers the work, add useful evidence or context there instead of creating a duplicate.

For bugs, include:

- affected URL or route
- expected behavior
- actual behavior
- reproducible steps
- browser/device where relevant
- screenshots or recordings when useful
- whether the problem is consistent or intermittent

Do not include credentials, private manuscript content, personal information, unpublished customer material, or security-sensitive details in public issues.

## Good pull requests

A strong PR is:

- focused on one coherent change
- easy to review
- clear about what changed and why
- tested at the smallest relevant level
- honest about limitations and incomplete work
- careful about user data, rights, accessibility, and provider status

Avoid bundling unrelated refactors with a feature or fix.

## Public data contributions

PocketAuthor includes public-facing directories and research surfaces. When adding or correcting entries:

1. Prefer primary or authoritative sources.
2. Include a source URL when the schema supports it.
3. Record the date checked when practical.
4. Distinguish confirmed facts from inferred or promotional claims.
5. Do not treat directory inclusion as endorsement.
6. Do not scrape or republish content in ways that violate terms, copyright, privacy, or applicable law.

## Writing and documentation

Write for the person trying to complete a real book task.

Prefer:

- concrete steps
- clear caveats
- primary sources
- examples with permission
- descriptive headings
- accessible language
- links that help readers act

Avoid unsupported guarantees about publishing, retailer acceptance, grants, sales, legal outcomes, or AI accuracy.

## Responsible AI and provenance

Do not present generated text as verified fact merely because it sounds plausible.

For factual, legal, historical, scientific, financial, or publishing-process claims:

- attach sources when appropriate
- preserve uncertainty
- distinguish quotation from paraphrase
- identify material requiring permission
- keep human approval at high-consequence steps

## Accessibility

New interfaces and public content should account for keyboard use, semantic structure, readable contrast, responsive layouts, alt text, reduced motion where relevant, and assistive technology.

## Security and privacy

Never commit:

- API keys
- database passwords
- service-role keys
- access tokens
- private customer manuscripts
- unredacted personal data
- production secrets
- third-party credentials

Report vulnerabilities privately using the instructions in [SECURITY.md](SECURITY.md).

## Commit and PR descriptions

Use descriptive commit messages and explain the user impact in the PR.

A useful PR description covers:

- problem
- approach
- verification
- screenshots for UI changes
- migration/data implications
- follow-up work

## Community behavior

Participation is governed by our [Code of Conduct](CODE_OF_CONDUCT.md).
